# Supervised staging acceptance

Candidate application commit `c0ae2ba53b3c6260107aaf1782aec1c7d80e22d3` on `test/isolated-pilot`. The acceptance scripts in this worktree run from the operator workstation. They are not part of the candidate deployment.

## Release and security gates

1. Release lead records a proposed **separate Vercel project** named `quizotab-staging`, the approved team and project IDs, deployment ID, operator, UTC start time and rollback contact. Disable automatic deployments from unrelated branches. Restrict access to all staging domains, preview URLs and immutable deployment URLs. Reserve a staging-only hostname under the operator's domain; the actual hostname, TLS certificate and protection settings require operator verification.
2. Database operator provisions a **separate staging Neon project** containing only synthetic fixtures and separate runtime, setup and owner credentials. Record independent project, branch, endpoint, direct hostname, database and roles from the control plane. Check login and effective roles on HTTP, transactional and direct connections against those pins. Check migration hashes, catalog, grants, triggers and closed admission. Reserve the retained pilot and recovery child for read-only comparison. Existing pilot commands deliberately pin the retained target; they cannot provision or certify a different staging project. A reviewed staging identity gate for the actual runtime and a separately approved bootstrap/fixture procedure are prerequisites to network exposure. Never satisfy that gate by turning off the pilot verifier.
3. Release operator selects the **Git SHA**, verifies the source archive against that SHA and uses the locked install, Next.js preset, repository root, Node 24 and `npm run build`. Set the stage deployment's server environment as below. A successful local build compiles and generates routes without proving runtime DB connectivity. On staging, inspect build logs for accidental secrets and require runtime identity confirmation at cold start before permitting any staff login.

| Server setting | Staging value and verification |
|---|---|
| `APP_URL` | Exact canonical HTTPS origin, no path; configure staging DNS and TLS to that origin. Redirect HTTP. Validate Host at the edge, strip client forwarding headers and set trusted forwarding information there. Exercise origin checks and Next.js Server Actions through the actual ingress. |
| `DATABASE_URL` | TLS pooled URL for the pinned staging runtime role only. Probe both database adapters. Verify the full scoring profile, append-only trigger, denied admission administration and denied journal/schema privileges. |

Set it to the **new staging project's** independently captured projectId, branchId, endpointId, directHost, database, runtimeRole and setupRole. The current parser requires database name `quizotab_pilot` even on a separate project. The setup role name is metadata; its credential stays offline. The release checker must require this variable: an absent manifest skips startup verification. Before exposing staging, demonstrate startup refusal with an incorrect branch ID in a private negative-control deployment that uses only the staging runtime credential. |
| `SESSION_SECRET`, `HMAC_SECRET` | Independent high-entropy staging values from the operator's secret store. Keep out of browser variables, build output and logs. Coordinate rotation across all serving deployments. Session-key rotation invalidates all issued sessions. HMAC rotation requires a guest-link/code reissue drill. |
| Mail and optional services | Use a controlled mail sink and staging-only SMTP settings if exercising reset. Disable real recipients. Leave unrelated media, payment and realtime integrations disconnected. Use production-mode Next.js for Secure cookies. |
| Excluded from runtime | Direct/setup/owner credentials, provider administrative tokens, development URLs, retained pilot pins and fixture-registration switches. Check environment scope and project IDs independently of variable names. Protect preview and immutable URLs too. |

4. Authenticate one owner, two judges and two room hosts through normal login on separate browser profiles. Confirm HttpOnly, Secure, SameSite=Lax, path, sign-out on shared devices, cross-origin mutation denial and normal same-origin writes. Try the wrong room and wrong tournament using synthetic accounts and expect denial and zero row changes. Revoke one assigned role and confirm the next request fails, then restore staffing under operator control. Privileged cookies currently last 30 days. Logout clears the local cookie; per-account revocation of an already issued owner cookie is unresolved. For a closed rehearsal, restrict ingress to named testers and agree on an emergency global key rotation and invalidation of old deployments. Public event use needs an accepted privileged-session policy.
5. Verify login and guest-code rate limits from the actual ingress, including a shared venue NAT. The application counts and records separately and uses forwarded client addresses. Enforce independent edge limits and masking of request bodies, URLs carrying codes, cookies and database parameters. An anonymous client should only reach the permitted spectator surface inside the rehearsal gate.
6. Keep deployment protection in force through smoke testing. Check login/logout, staff assignments, release coverage, one approved synthetic submission and independent review, opted-in room/global spectator totals, and sharing revocation. Measure latency, pool waiters, lock waits and errors through the actual route. Stop and reconcile uncertain writes before proceeding.
7. To roll back, pause fixture activity, record last acknowledged IDs and close external access. In the staging project select the previously recorded known-good deployment and reassign the **staging** alias; verify the resulting project, commit, origin, DB identity and privileges. On a first deployment with no good predecessor keep access closed. Rollback can restore earlier environment settings, so check credential versions and invalidate old sessions before reopening. A code rollback does not roll back score history. Use read-only reconciliation before any separately authorized data repair. ## Reproducible event traffic

Use a new, synthetic two-room championship for each run. Four teams, two per room, one owner, two distinct judges and two independent reviewers. Preconfigure enough **distinct eligible slots** per fixture (one question per minute for each team for the scored duration). Freeze the config revision and input sheet before release. Use points `(roomIndex + teamIndex + questionIndex) % 4` within a 0–3 range. Persist the request UUID alongside each slot in the restricted driver ledger; never regenerate it on timeout. Precompute expected per-team sums and event counts from the ledger.

| Level | Spectators | Duration | Spectator GET/s | Staff pattern |
|---|---:|---:|---:|---|
| Smoke | 6 | 3 min | 1 | Full normal login, release, score and close |
| Small event | 30 | 15 min | 5 | Both rooms active; alternate overall and room standings |
| Headroom | 60 | 10 min | 10 | Same actors and scoring cadence; start only after small-event pass |

Use separate sessions; half the spectators follow room standings, the remainder tournament standings. Stagger initial polls uniformly across the six-second refresh interval and retain each session's phase. For each minute both judges submit for both teams (four POSTs/min). Hosts review within 10 s (four decision POSTs/min). Expected totals at the 15-minute level are 60 entries, 60 submissions, 60 approvals, two closures and 4,500 scheduled spectator reads before retries or pauses. Poll staff workspaces on their normal 12-second cadence; each judge reads workspace and each host also reads pending and completion. That adds about 0.67 GET/s across four staff, plus one owner monitoring read every 15 s and 0.13 scoring/review POSTs/s. Count actual requests, including extra refresh after mutations and owner release/close reads. Record distinct pending, approved and completed views. Smoke and larger levels use fresh fixtures.

Sample every five seconds. Record actual concurrency and requests/s by route/status, latency p50/p95/p99 and max (nearest rank), timeout/error counts, process RSS, per-instance pool total/idle/waiting, live backend count, `pg_stat_activity.wait_event_type` and `pg_blocking_pids(pid)`. Collect queue wait separately from transaction duration. If the deployed pool metrics are inaccessible, establish staging-only instrumentation before running the load gate. Restrict DB telemetry to the monitoring operator; export counts and durations only. Record time from releasing a controlled pause until queue drain and successful staff read. Compare end-state history and public totals with the ledger. Also test one correction, one denial and interrupted submission in a separate labeled fixture.

**Proposed limits for operator sign-off:** stop immediately on any authorization, privacy, scoring, audit or identity mismatch, unexpected admission change or unconfirmed write. Pause on any pool checkout timeout, any lock wait over 5 s, or unexpected 5xx/timeouts above 1% in a rolling minute. Fail a level if successful read p95 exceeds 1 s or write p95 exceeds 2 s for two consecutive minutes, p99 exceeds 5 s for the level, queue utilization exceeds 80% of configured pool capacity for a minute, or RSS exceeds 80% of the function limit. Require queue drain and usable staff views within 30 s of stopping new traffic. Compare peak and post-drain RSS over repeated levels. These are proposed acceptance limits. The 68-call PGlite benchmark in EVENT_READINESS.md is a local service baseline only.

## Recovery drill and evidence

The repository records the retained schema and results. It supplies no independently approved backup ID, retention period, timestamp or restore authorization. The proposed Neon mechanism is a **separate child branch from past data** within the parent's actual history window. The database operator must confirm availability, cost, access controls and source cutoff first. A local template copy validates the reconciliation method; it cannot establish provider retention or disaster recovery time. [Neon branch creation and history](https://neon.com/docs/manage/branches)

1. Record the retained project, source branch and endpoint from the independently approved manifest. Freeze writes throughout capture and verification. Record UTC cutoff, last committed scoring and lifecycle events, count and official totals. Require a cutoff after the last intended commit and within the confirmed history window. Obtain separate operator approval for child creation and credential access. Do not run an in-place restore.
2. Start the recovery clock. In the approved pilot project choose **Branches → New branch**, select the approved source by branch ID, choose **Past data**, enter that UTC cutoff and name the new child `qt-restore-drill-<UTC>`. Record the returned child branch and compute endpoint IDs and separately confirm its parent and timestamp in the control plane. Keep all application traffic off the recovery target. Treat copied roles and credentials as sensitive.
3. Prepare private source and child pins in the existing seven-field manifest format. Use separate setup credential files containing `DATABASE_URL_UNPOOLED` for each direct setup login. Verify project, database and role names match, and branch, endpoint and direct hostname differ. Retain evidence files outside Git. From a clean shell, after separate live-read approval, run the following from this worktree:

   `node --conditions=react-server --import tsx scripts/verify-restore.mjs "<absolute-source-pins>" "<absolute-source-setup.env>" "<absolute-child-pins>" "<absolute-child-setup.env>"`

4. The checker opens read-only repeatable-read transactions, checks actual identities, migration hashes and journal timestamps, post-upgrade fingerprint, triggers, admission state, empty allowlist and full privilege matrix. It compares ordered row digests of entries, events, teams, tournaments, staff and tournament state plus independently recomputed effective points by team and tournament. Confirm the signed-off baseline from EVENT_READINESS.md (10 entries, 21 events, Amber 3, Cobalt 8, Jade 4, Ochre 6) still applies at the chosen cutoff. Record UTC finish and discrepancies. Proposed gate: zero lost acknowledged writes at the cutoff, exact history equality and operator verification within 30 minutes of starting recovery.
5. If source changes during the drill, invalidate the comparison. If a digest or identity differs, keep the child isolated, preserve evidence and escalate. Do not overwrite either database or update expected hashes. Any later retirement, credential change or retention extension requires operator approval. A branch-only rehearsal leaves cross-project or provider-loss recovery unproven.

## Acceptance record

### Local execution evidence

From the checkout, run `node --conditions=react-server --import tsx scripts/test-pilot-admission-race.mjs "<absolute-local-PostgreSQL-bin-directory>" --scoring --load`. The runner initializes a new SCRAM-protected loopback cluster on a dynamic port, exercises actual restricted-role SQL sessions, then stops the server and removes the synthetic cluster. The scoring fixtures project the engine read for their synthetic tournament. The separate admission race uses the actual database trigger. PostgreSQL 18.4 Windows binaries came from the version-pinned portable package; no dependency or lockfile change is required. [Portable binary package](https://www.npmjs.com/package/@embedded-postgres/windows-x64)

The final run observed separate writer PIDs 8788 and 26724 and both writers queued on the tournament lock. Duplicate and conflicting UUID races, independent room writes, competing decisions and corrections, revocation, duplicate closure and reopening against draw release passed. Revocation won its race on this run; the subsequent judge submission was denied. The injected failed audit insert rolled back the entry. The application wrapper discarded the checkout after a real local commit whose successful reply was suppressed in the client. The observer found exactly one matching entry and the idempotent retry returned the original receipt. This tests ambiguous commit handling without simulating a Neon WebSocket partition.

The three-minute **local service** smoke exercised one owner, two judges, two room hosts and six synthetic spectator polling streams. It completed 339 operations at 1.89/s, peak six concurrent calls, zero errors, 12 approved entries, 24 events, two closures and team points 3/6/6/5. Native pool maximum eight; five-second samples saw at most six checked-out connections, zero queued checkouts and zero lock waiters. Sampling can miss short waits. Peak sampled process RSS was 157 MiB. Draining the completed workload, closing and reconciling took 78 ms. This is a post-load drain measurement; venue outage recovery remains unmeasured.
